# Discord をAI(Claude Code)が見る・操作する方法

**方法はブラウザ操作(`mcp__claude-in-chrome__*`)に決めた。** BotやMCPは使わない。2026-09-22に確定。

> [!important] なぜBot・自作MCPではないか
> - **公式のDiscord MCP(本人のアカウントとして読み書きできるもの)は存在しない**(2026-09-22調査）。
>   Anthropicは Claude Code の自社Discordコミュニティ用プラグインを持つが、任意ユーザーのアカウント連携ではない。
> - **個人製のDiscord MCPは、すべてBotトークンで動く。** Botは別人格で、**DM(個人宛のダイレクトメッセージ)は読めず、
>   本人のアカウント設定も変えられない。** 今回やりたいこと(DMを含む通知の確認、アカウント・サーバー設定)には合わない。
> - **本人のアカウントを自動操作する「セルフボット」はDiscordの利用規約違反で、アカウント停止のリスクがある**
>   (User Token を使う自動化は禁止。Bot Account の仕組みを使うのが公式の唯一の自動化手段)。
> - Raspberry Pi の OpenClaw(→ [`raspberry_pi.md`](./raspberry_pi.md))は**Botとしての応答**用で、
>   これも別人格。今回の用途とは別物として残す(使わない方針は本人確認済み、2026-09-22)。
> - **サークルのサーバーにBotを立てる案は不要**(2026-09-22)。本人はサークルの幹事長を引退し、
>   サーバーの管理権限は次の人に移行済み。**「自分が管理者のサーバー」がそもそも無い前提で考える。**
>
> **結論: ブラウザでログイン済みの Discord(`discord.com/app`)を、Claude in Chrome で操作する。**
> 保管庫の既定ブラウザルール(macOS の Chrome、プロフィール `<自分のプロフィール>`。→ [`../AGENTS.md`](../AGENTS.md))がそのまま使える。
> ログイン状態も既存の Chrome セッションのまま引き継がれる(2026-09-22、`kmiyazaw` としてログイン済みを確認)。
> **対象は、本人が参加している全サーバー・全DM。**管理者かどうかは問わない(閲覧・返信は管理者権限が無くてもできる。
> 設定変更が要る場面では、そのサーバー/機能で本人に権限があるかをその都度確認する)。

## できること(確認済み・2026-09-22)

- フレンド一覧、DM一覧(左サイドバー)、サーバー一覧、未読バッジの閲覧。
- 会話を開いて内容を読む、検索する。
- 返信の送信(**送信は「書き込み系」。実行前に本人へ内容を見せて許可を取る**、通常のブラウザ操作の基準どおり)。
- アカウント設定・通知設定・サーバーの整理(チャンネル並べ替え、ロール設定など)。**設定変更も同様に事前確認**。

## 使い方(依頼の型)

本人が「Discordに新着があるので見て」のように依頼したら:
1. `navigate` で `https://discord.com/app` を開く(既存ログインのまま入れる)。
2. 未読バッジのあるサーバー/DMを開いて内容を読む(**下の「取得方法のルール」に従う**)。
3. 内容を要約して報告する。返信が要るときは、本人と相談して文面を決め、**送信前に確認を取ってから**送る。

**新着の自動監視はできない。** ブラウザ操作は毎回こちらから開きに行く方式で、Discord側からのプッシュ通知をこのセッションが受け取る仕組みはない。
本人が気づいたときに依頼する、という運用(本人の希望どおり)。

## 取得方法のルール(スクリーンショット vs テキスト取得) — 必読

> [!important] 既定はテキスト取得。スクリーンショットは限定的な場合だけ
> **スクリーンショットは画像トークンを大量に消費する。** Discord は通常の DOM を持つ SPA なので、
> `get_page_text` で軽く読める(2026-09-22 実測: フレンド一覧・オンライン状況が、画像なしでそのまま文字列で返った)。
> **他のブラウザ操作と同様「両方から届くなら軽い方」の原則がここでも成り立つ**(→ [`../AGENTS.md`](../AGENTS.md) の
> 「両方から届くなら、必ず MCP を選ぶ」と同じ考え方。ここでは MCP ではなく取得手段の選択に適用する)。

**優先順位（毎回この順で試す）**

1. **`get_page_text`** — 会話・メッセージ・一覧を読む、要約する、検索する。**第一選択。** 画像を一切使わない。
2. **`read_page`**(`filter: "interactive"`)— ボタン・リンク・送信先など、クリックすべき要素の座標や ref を知りたいとき。
   これもテキストのみで、`find` と組み合わせて要素の `ref` を取り、`computer` の `click` に `ref` を渡せば
   スクリーンショットなしでクリックできる。
3. **`computer screenshot`**(スクリーンショット)— **次のいずれかに該当するときだけ**使う:
   - 画像・スタンプ・絵文字・添付ファイルなど、**テキストでは伝わらない視覚情報**を確認する必要があるとき。
   - `get_page_text`/`read_page`/`find` で目的の要素が見つからず、**座標クリックのために実際の画面を見る**必要があるとき。
   - 本人に**実際の見た目そのもの**を見せる必要があるとき(`save_to_disk` で共有する場合)。
   - それでも使うときは `scale` を下げる(既定 1 → `0.5` 程度)。全画面を毎回原寸で撮らない。

**やってはいけないこと**: 「とりあえず状況を確認するためにスクリーンショットを撮る」という使い方をしない。
まず `get_page_text` を試し、それで用が足りるかを先に判断する。1つの会話やチャンネルを読むのに、
スクリーンショットを何枚も連続で撮る（スクロールのたびに撮る等）のは避ける——テキストなら一度の呼び出しで
ページ全体（表示中の範囲）が返る。

**このルールは Discord に限らず、他サイトのブラウザ操作にも同じ考え方で適用してよい**
（Discord は SPA で特にテキスト取得が効きやすい実例として、ここに書いた）。

## 未読・メンションの読み方とサーバーの既読（2026-10-15 に確認、`/discord`）

- **未読の一覧**: サーバーアイコン（`[data-list-item-id^="guildsnav___"]`）の `aria-label` が「N 件のメンション、<名前>」「未読メッセージ（<名前>）」になる。
  `nav` で絞ると0件になることがあったので絞らない。読み込み直後は空のことがあり、数秒待ってから読む。既読にした直後は `aria-label` が `null` になることがあり、目視（`zoom`）で確かめた。
  DM は `[data-list-item-id^="private-channels"]` の `aria-label` が「N件の未読、<名前>(ダイレクトメッセージ)」。
- **メンション**: 右上の「受信ボックス」（`aria-label="受信ボックス"`）→「メンション」タブ。`[role="dialog"]` 内の `[id^="message-content-"]` の `innerText` で本文が取れる。
  サーバー・チャンネル・時刻は `[class*="channelName"]` などで取れる。**このタブは過去のメンションも並ぶ**ので、未読バッジの件数と時刻で新しいものだけ拾う。
  パネル全体の `innerText` をそのまま返すと、URL のクエリ文字列が含まれて Chrome 拡張に止められた（`[BLOCKED: Cookie/query string data]`）。URL を `<URL>` に置き換え、`=?&` を消してから返す。
- **DM を開くと既読が付く。** DM の中身を読む方法は、開く以外に見つかっていない。
- **サーバーを既読にする**: アイコンを `find` で探し、`computer` の `right_click`（`ref` 指定）→ メニュー「サーバー操作」の「既読にする」。
  `find` の ref をクリックしても効かなかったので、`javascript_tool` でメニュー項目の座標を取って `left_click` した。タブのタイトルの未読数が減るので、それで確かめられる。
  JS で `contextmenu` イベントを送ってもメニューは開かなかった。

## メッセージ入力のルール — `type` は使わない

> [!warning] 2026-09-25 に崩れた文面を送ってしまった
> - `computer` の `type` で日本語混じりの文を打つと、**IME が挟まって半角数字と改行が抜ける**（「11/13、20」→「、、」）。
> - 入力欄は Slate エディタで、**DOM（`innerText`・見た目）を消しても内部状態に前の文面が残り**、送信時にそれも一緒に出た。
>   `execCommand('selectAll'/'delete')` では内部状態が消えない。

**手順（これで正しく送れた）**
1. 入力欄をクリック（または編集時は空の入力欄で `Up` キー）。
2. **中身を消すのは実キー**: `key` で `cmd+a Backspace`。
   `find` の ref をクリックしても入力欄にフォーカスが入らず、キーが効かないことがある（2026-09-28）。
   そのときは入力欄の**座標をクリック**してから `cmd+a` → `Backspace` を別々に押し、`innerText` が空になったのを確かめてから貼り付ける。
3. **文面は貼り付けイベントで入れる**: `javascript_tool` で `DataTransfer` に `text/plain` を入れ、
   `ClipboardEvent('paste')` を入力欄に dispatch する（改行は `\n` のまま入る）。
4. **送る前に `zoom` で入力欄を見て、文面どおりか確かめる**（`innerText` だけで判断しない）。
5. `Return` で送信／保存。

送ってしまった誤りは、空の入力欄で `Up` → 上と同じ手順で**自分のメッセージを編集**して直せる（「編集済」が付く）。

## 送信結果の確認

画面にメッセージが出ただけで送信完了と扱わず、DMを開き直して残っていることを確かめる。418の3周年の案内では、送信直後には表示されても、開き直すと消える例があった。警告が出ないことも成功の証拠にはならなかった。

残っていない場合は「到達不明」とする。この案内では本人が到達不明を未送信として管理すると決めたが、未到達が確定したわけではない。繰り返し再送しても消えたため、自動で再送を重ねず止める。残りは本人が送り、全員への送信後に作業用メモの削除を指示した。過去の宛先一覧や未送信メモは復元して再実行しない。
