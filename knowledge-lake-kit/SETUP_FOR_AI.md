# 初期構築の手順書（AI 向け）

あなた（Codex / Claude Code）は、このキットを使って、利用者の新しい Obsidian 保管庫を構築する。
利用者は保管庫をほぼ作っていない。**作業の目的は「器を整え、最初の中身を一緒に入れ、運用を始められる状態にする」こと。**

日本語で会話する。推測で埋めず、分からないことは利用者に聞くか「未確認」と書く。

## 0. 全体を把握する

最初に次を読む。

1. `knowledge-lake-kit/START_HERE.md`
2. `knowledge-lake-kit/guide/01_philosophy.md`（この方式の考え方。以降の判断の基準）
3. `knowledge-lake-kit/vault/AGENTS.md`（構築後にあなた自身が従う指示書の原型）

読んだら、利用者に「これから何をするか」を5行以内で説明してから始める。

## 1. 現状を確認する

- カレントディレクトリが保管庫にするフォルダか確認する。既にファイルがあれば一覧を見せ、**上書きしない**。既存ファイルとの統合方針を利用者に確認する。
- `git`・`python3` があるか確認する（無ければ後回しでよい。Git なしでも構築は進める）。
- 使っている AI が Codex か Claude Code か、両方かを聞く。

## 2. 構成を決める（インタビュー①）

`vault/` には次の名前空間がある。**全部作る必要はない。** 利用者の生活に合わせて取捨選択する。

| フォルダ | 用途 |
| --- | --- |
| `00_self/` | 自分についての一次情報（必須） |
| `01_diary/` | 日記 |
| `02_note/` | 汎用メモ・調べもの・判断の記録（必須） |
| `03_hobby/` | 趣味 |
| `04_misc/` | どこにも入らないもの |
| `05_home/` | 住まい・持ち物・家電・PC |
| `06_health/` | 健康・通院・検査（機微） |
| `07_money/` | お金の判断の文脈（台帳は作らない） |
| `08_people/` | 人物（機微） |
| `10_work/` | 仕事・バイト |
| `30_study/` | 学業・研究・資格 |
| `79_template/` | テンプレート（必須） |
| `89_profile/` | 外部向けの自分（履歴書・自己紹介文の下書き） |
| `99_public/` | 公開する文章（ブログ等） |
| `tmp/` | 一時置き場（Git 管理外。必須） |

利用者に聞くこと（まとめて1回で聞く）:

1. 今の立場（学生 / 会社員 / フリーランス / 経営者 など）。会社や組織を持っていれば `20_company/` を足す。
2. 上の表で要らないフォルダ、足したいフォルダ（例: 投資なら `09_investment/`、特定の学校なら `42_xxx/`）。
3. 日記を書くか。書くなら PC とスマホのどちらで書くか。
4. 公開ブログ・ポートフォリオを持つ予定があるか（無ければ `89_profile/`・`99_public/` は作らない）。

**番号は上下関係ではなく、用途別の並列名前空間。** 足すときは空いている番号を使い、意味のある近さで選ぶ（例: 生活系は一桁、仕事系は10番台、学業は30番台）。

## 3. ひな形をコピーする

- `knowledge-lake-kit/vault/` の中身を保管庫のルートへコピーする。ドット付き（`.codex/`・`.gitignore`）も含める。
- 不要と言われたフォルダはコピーしない。そのフォルダへの言及を `README.md`・`AGENTS.md` から消す。
- 追加フォルダには、既存 README と同じ形（「何を集めるか」「何を集めないか」「取り扱い」「入口」）で README を作る。
- コピー後、`knowledge-lake-kit/guide/` は `02_note/knowledge-lake-method/` へ移す（運用の原本として保管庫内に残す。リンクは相対パスで直す）。
- `knowledge-lake-kit/` 自体は、構築の最後に利用者の許可を取ってから削除する。

## 4. AI の設定を合わせる

### Codex を使う場合

1. `.codex/config.toml` はそのまま使える（`AGENTS.md` を末尾まで読ませる設定と hooks の有効化）。
2. `.codex/hooks.json` の `__VAULT_ROOT__` を保管庫の絶対パスに置き換える。
3. `tools/codex-hooks/guard.py` の冒頭の設定（`PUBLIC_AREAS`・`PRIVATE_PATTERNS`）を、手順2で決めた構成に合わせる。公開フォルダを作らないなら `PUBLIC_AREAS = ()` にする。
4. `python3 -m unittest discover -s tools/codex-hooks -v` でテストを通す。
5. 利用者に、Codex の `/hooks` で新しいフックを確認・信頼してもらう（**信頼確認を迂回しない。** 利用者本人が承認する）。

### Claude Code を使う場合

1. ルートに `CLAUDE.md` を作り、中身は `@AGENTS.md` の1行だけにする（指示書を1本に保つため）。
2. `.claude/settings.json` を `guide/03_ai-permissions.md` の「Claude Code の設定例」から作る。接続していない MCP の行は入れない。

### 両方使う場合

両方やる。**指示書は `AGENTS.md` 1本**に保ち、AI ごとに別の指示書を書かない。

## 5. 自分の情報を入れる（インタビュー②）

`00_self/` を埋める。**一度に全部聞かない。** 次の順に、各ファイル3〜6問ずつ、答えやすい形で聞く。
答えは利用者の言葉をなるべく残して書く。盛らない・美化しない。

1. `identity.md` — 名前（呼ばれたい名前）、所属、住んでいる地域（市区町村まででよい）、使っている端末
2. `now.md` — 今のフェーズを一言で、進行中のこと（表に5〜10行）、今いちばん気にしていること。**更新日を必ず書く**
3. `values-principles.md` — 大事にしていること、苦手な進め方、**AI にどう振る舞ってほしいか**（例: 結論から言う / 根拠を出す / 決めつけない / 感情の話は先に聞く）
4. `timeline.md` — 学歴・職歴・引っ越し・大きな出来事を年単位で。分からない年は「未確認」
5. `glossary.md` — 普段使う略称、所属組織、プロジェクト名

`decisions/` は空でよい。ただし、インタビュー中に「なぜそうしたか」が語られた大きな決断（進学、転職、引っ越しなど）があれば、1件だけテンプレートで書いてみせ、書き方を体験してもらう。

## 6. Git を始める

利用者が同意すれば:

1. `git init`、最初のコミット。`.gitignore` を確認してから `git add` する（`tmp/` が除外されていること）。
2. GitHub に **private** リポジトリを作って push する（`gh` があれば `gh repo create --private`）。公開リポジトリにしない。
3. 日記をスマホで書くなら、`guide/05_git-and-phone.md` の「日記だけ別リポジトリにする」を読んで、やるかどうか利用者に聞く。最初はやらなくてよい。

## 7. 仕上げ

- `README.md` の構成一覧と、実在するフォルダが一致しているか確認する。
- 全 README の相対リンクが切れていないか確認する（`grep -o '](\./[^)]*)'` などで拾って実在確認）。
- `hygiene.base` を Obsidian で開くと、`updated`・`visibility` が無いノートの一覧が出ることを伝える。
- 利用者に次を伝えて終わる:
  - 普段は「〜について調べて、ノートにまとめて」「今日あったことを now.md に反映して」のように頼めばよい
  - 1ヶ月の育て方は `02_note/knowledge-lake-method/06_growing.md`
  - タスク管理を始めるなら `02_note/knowledge-lake-method/02_tasks.md`

## 止まる条件

- 既存ファイルを上書き・削除しそうなとき
- 公開リポジトリ・公開サイトへ何かを出そうとするとき
- 外部サービスへのログイン・連携が必要なとき（何のために、どのアカウントで、を先に説明して許可を取る）
- 健康・お金・他人についての情報を、利用者が自分から話していないのに聞き出そうとしているとき（聞かない）
