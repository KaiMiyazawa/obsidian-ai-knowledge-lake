# AGENTS.md

この保管庫は、長期的な共同記憶として扱う。
作業時は、単発の修正ではなく、後から AI が再利用しやすい文脈を残すことを優先する。

> このファイルは Codex・Claude Code の両方が読む唯一の指示書。AI ごとに別の指示書を作らない
> （Claude Code はルートの `CLAUDE.md` に `@AGENTS.md` と1行だけ書いて読ませる）。
> 運用していて「毎回同じことを言っている」と気づいたら、ここに1項目足す。

## まず読むもの

- [`README.md`](./README.md)
- [`00_self/`](./00_self/README.md) … 私が誰で、今どのフェーズにいるか。特に [`00_self/now.md`](./00_self/now.md) は時点依存なので**更新日を確認する。**
- その作業に直接関係する領域の README
- 既存の関連ノート

## 基本原則

- 日本語で会話する。
- **推測で補わず、見つかる事実を優先する。** 分からないことは「未確認」と書く。
- 変更は最小限にしつつ、将来の再利用性は落とさない。
- **一時的な作業メモと、残すべき知識を分ける。** 作業メモは `tmp/` かタスク管理側へ。
- 画像、添付、参照リンクは壊さない。
- 既存の構成や命名を、理由なく崩さない。
- **文書の性質で、上書きか追記かを選ぶ。**
  - 判断の理由（なぜそうしたか・なぜ見送ったか）は残す価値があるので追記してよい。
  - 手順・現状のステータスなど「今の正解」だけで足りる文書は、古い記述を消して上書きする。
  - 日付入りの経過ログ（いつ何を実行し何が起きたか）を積み重ねない。読むたびに文脈を食うため。

## 記録の考え方

- 番号付きフォルダは上下関係ではなく、**用途別の並列名前空間。**
- **各フォルダの README が、その領域の使い方の一次ソース。** 新しいノートを置く前に読む。
- 経歴の原本は [`00_self/timeline.md`](./00_self/timeline.md)。`89_profile/`（外部向けの自分）は事実を持たず、見せ方だけを持つ派生。
- **同じ内容を重複させず、原本を決めて相互参照する。** 二重管理は必ずずれる。
- 個人的な事実でも、**将来の AI が独立して読める形**で書く（「あれ」「例の件」と書かない。固有名詞は [`00_self/glossary.md`](./00_self/glossary.md) に足す）。
- 時点依存の情報には日付を書く。

## ノートの形式

- ファイル名は英語の kebab-case（`moving-2026.md`）、本文は日本語。
- frontmatter は最低限これだけ付ける（`hygiene.base` が欠落を一覧にする）。

```yaml
---
visibility: private   # private / public
updated: 2026-01-01
---
```

- **保管庫内のリンクと画像は、相対パスの Markdown リンクで書く**（`[表示名](./note.md)`、`![](./images/x.png)`）。
  wikilink（`[[note]]`）は使わない。理由: AI が名前検索なしでそのまま開ける（`README.md` は大量に同名になる）、GitHub 上でもたどれる、Obsidian の名前変更時の自動更新も効く。
  Obsidian 側は「設定 → ファイルとリンク」で `Wikilink を使用` をオフ、`新規リンクの形式` を「現在のファイルからの相対パス」にする。空白を含むパスは `%20` にする。
- 画像や添付は、参照するノートの近く（同じフォルダの `images/`・`documents/`）に置く。
- 強調したい前提は Obsidian の callout（`> [!important]`、`> [!warning]`、`> [!note]`）で書く。

## 判断の記録 — 決めたことは「なぜ」と一緒に残す

- 大きな決断は [`00_self/decisions/`](./00_self/decisions/README.md) に1決定1ファイルで残す（背景・選択肢・決め手・前提が崩れる条件・その後）。
- 小さな運用判断（「このサービスは使わない」「この MCP は入れない」）は、関係するノートに**理由付きで**1〜2行残す。
  次に同じ検討をしたとき、AI が同じ調査をやり直さずに済む。

## タスク管理 — 実行タスクは保管庫に書かない

実行タスク（「〜する」「〜を確認する」）は、ノートに `- [ ]` を追記せず、タスク管理ツールに作る。
詳細は [`02_note/knowledge-lake-method/02_tasks.md`](./02_note/knowledge-lake-method/02_tasks.md)。

- 保管庫に残すのは、**やらないと決めたこと・方針として決まったこと**という判断の記録だけ。
- タスクを作るとき、次に着手する人や AI が前提を調べ直しそうなら、notes に「目的・手順・関係ノートのパス・止める条件」を書く。
- 「TODO は何ある？」と聞かれたら、タスク管理ツール側を見て答える。

## 手段の選び方 — API / MCP を先に試し、届かないものはブラウザへ

接続済みの MCP と、検討して見送ったものの一覧は [`02_note/mcp-inventory.md`](./02_note/mcp-inventory.md) が原本。

1. **ローカルのファイルとCLIで済むなら、それでやる。** 保管庫はローカルにあるので、Obsidian 用の MCP は要らない。
2. **MCP / API で完了できるなら、そちらでやる。** 速く、確実で、文脈の消費が小さい。
3. **API に無い操作は、ブラウザ操作で触る。** 「AI にはできないので手作業で」と言う前に、ブラウザで届くか確かめる。
4. **判断が要るものは自動化しない。** 人が決める。

**両方から届くなら、必ず MCP を選ぶ。** ブラウザ操作はスクリーンショットで文脈を大量に使う。「ブラウザでもできる」はブラウザを使う理由にならない。
3クリックで終わる設定変更を自動化しても割に合わない。自動化の価値は「まとめて片付けるとき」と「手順を残して再現したいとき」に出る。

**どのサービスにどのアカウントで繋がっているかは [`02_note/services-accounts.md`](./02_note/services-accounts.md)。** サービスを触る前に読む。

## 確認が要る操作

読み取り（検索・要約・件数確認）は断りなくしてよい。次は**実行前に内容を見せて許可を取る。**

- メール・メッセージの送信、予定への招待
- ファイル・メール・予定の削除、共有範囲の変更
- 購入・支払い・契約
- 公開リポジトリ・公開サイトへの反映
- 外部サービスへのログイン（何のために・どのアカウントで・どの認証方法で、を先に示す）

ブラウザ操作で書き込むときは、1件ずつ変更前の画面を確認し、一括削除はせず、確認ダイアログが出たら内容を報告して指示を待つ。エラーは2回までで止めて報告する。
**手順は使い捨てにせず、関係するノートに残す。** 同じ操作は繰り返し発生する。

秘密の値（パスワード・APIキー・トークン）は、保管庫・Git・チャットに書き写さない。

## 開発中のコードと大量データは保管庫の外、または `.` 付きフォルダへ

- 独立した Git リポジトリ・`node_modules`・`.venv` を持つプロジェクトは保管庫の外（例: `~/Documents/<名前>/`）に置き、保管庫には判断と参照だけを残す。
- 保管庫の中に置く大量の生データ（数千件のファイル）は `.data/` などドット付きフォルダに入れる（Obsidian はドット付きフォルダを読み込まないので重くならない）。
- ノートから埋め込む画像はドット付きフォルダに入れない（表示されなくなる）。

## Git 運用

- **ステージ（`git add`）する前に、必ず `git pull --rebase --autostash` を実行する。** スマホなど別の場所からリモートが進んでいることがある。autostash はステージを外すので、add の後に pull しない。
- push が拒否されたら、強制せずに取り込んでからやり直す。`--force` は使わない。
- `git add -A` を使うときは、先に `git status` で全件を目視する。意図しない削除を1件でも見つけたら、パスを個別に指定する。
- 詳細は [`02_note/knowledge-lake-method/05_git-and-phone.md`](./02_note/knowledge-lake-method/05_git-and-phone.md)。

## 分からない語が出てきたら

保管庫にない固有名詞や、意味の取れない略称が出てきたら、**まず自分で Web 検索する。**
本人に聞くのは、検索しても分からなかったときか、解釈が複数あるときだけ。先に聞いてから調べるのではなく、**調べてから確認を取る。**

- 分かったことは [`00_self/glossary.md`](./00_self/glossary.md) か関連ノートに書く。**出典 URL と調査日を添える。**
- 検索結果と本人の説明が食い違ったら、本人の説明を優先し、食い違いがあった事実も残す。
- 人物・組織は公開されている professional な情報だけを扱う。確定できなければ「未確認」。

## 編集時の注意

- 既存のリンクや画像パスを確認してから移動する。移動したら参照元を全件直す。
- ドキュメントを編集したら、関連ノートや README の目次の更新が要るか確認する。
- 機微情報の扱いは、各フォルダの README の「取り扱い」に従う。
- `89_profile/`・`99_public/`（外に出す前提）と、それ以外の間で内容を写すときは必ず立ち止まる。公開側から非公開ノートへリンクを張らない（ファイル名だけで中身が分かることがある）。
- 不要なファイル削除や大規模移動は、影響範囲を確認してから行う。
- 整理は階層を増やす前に、薄いノートの統合と README への入口集約を検討する。
